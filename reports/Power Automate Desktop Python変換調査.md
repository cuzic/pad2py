# 非公開フォーマットでもPAD変換基盤は組み立てられる

Power Automate Desktop(PAD)のフロー定義フォーマットは、クラウドフロー(Logic Apps系)と違って**公式にスキーマが公開されておらず**、ローカルディスク上の単体`.flow`ファイルとしてエクスポートする公式GUI機能も存在しない([Dataverse workflow テーブル reference](https://learn.microsoft.com/power-apps/developer/data-platform/reference/entities/workflow)、[UiPath Marketplace PAD_ExportFlows](https://marketplace.uipath.com/listings/export-power-automate-desktop-pad-flows))。これはPAD→Python変換プログラムの最大の障壁だが、迂回路は存在する——PADデザイナーの「コピー&ペースト」機能が吐き出す**行指向のテキストDSL**は構文が単純で、実例(GitHub `Hardik-S/geodata`)で直接確認できており、これを一次入力とすれば公式フォーマットの完全解読を待たずにパーサーを組める。アクション単位の変換は、ウィンドウ操作・マウス/キーボード操作・待機系の大半がpywinauto/pyautoguiへ機械的に対応付け可能であることも確認できたが、UI要素セレクタの変換は属性レベルでは移植できる一方、`AutomationId`の不安定性やElectron系アプリの取得困難といった**変換後も残る脆さ**を引き継ぐ。業界を見渡すと、PADに限らずRPAツール間のフロー→コード完全自動変換を実現したOSS/学術研究はほとんど存在せず、商用移行ツールもすべて「アクセラレータ+人手レビュー」止まりであるという一致した経験則がある。したがって本プロジェクトは、公式フォーマットの完全解読を前提にせず、**忠実な1:1変換をデフォルトとし、未対応要素は目立つTODOとして残すフォールバック戦略**を軸に、パーサー→IR→コードジェネレータの三層アーキテクチャをVisitorパターンで実装するのが最も現実的な設計となる。技術的な実現可能性は「全自動変換」としては低いが、「開発者の手戻りを大幅に減らす半自動変換支援ツール」としてなら十分に実現可能である。

## PADのフロー保存形式は非公開であり、クリップボードのテキストDSLが唯一の実用的な突破口

PAD(クラウド接続版)のフロー定義の正本は、ローカルファイルではなく**Dataverseの`workflow`テーブル**に格納されている。`clientdata`という列が「フロー定義とconnectionReferencesをエンコードした文字列のJSON」を保持し、デスクトップフロー専用の追加列`desktopflowmodules`と専用テーブル`desktopflowmodule`が実際のアクション本体を別領域に保持していると見られる([Process (Workflow) table reference](https://learn.microsoft.com/power-apps/developer/data-platform/reference/entities/workflow)、[desktopflowmodule table reference](https://learn.microsoft.com/en-ie/power-apps/developer/data-platform/reference/entities/desktopflowmodule))。さらに厄介なのは、Power Usersコミュニティの一次証言によれば、ソリューションエクスポート時に得られるJSONの中身が以前は「エンコードされたパッケージ記述」だったのに対し、**「Schema V2」ではこの文字列が廃止され「デスクトップフローのバイナリ」に置き換わった**という点だ([Power Users community thread](https://powerusers.microsoft.com/t5/Power-Automate-Desktop/Governance-Monitoring-Power-Automate-Desktop-Flows/m-p/2656902))。つまりMicrosoftは意図的にせよ結果的にせよ、フォーマットを時間軸でブラックボックス化させており、単純な固定スキーマのパーサーを書いても特定バージョンでしか動かないリスクがある。ローカルキャッシュも単一ファイルではなく`C:\Users\[User]\AppData\Local\Microsoft\Power Automate Desktop\Console\Workspace`配下の**フォルダ構造**であり、クラウド同期前提でPAD自身もこのキャッシュから復元できないと報告されている([DEV Community](https://dev.to/01kg/power-automate-desktop-flow-local-folder-2aa5))。UiPath Marketplace製の`PAD_ExportFlows`/`PAD_ImportFlows`も「PADはフローのエクスポート/バックアップを許可していない」と明言し、代替としてWinAutomation由来の独自テキスト形式(サブフローを`.subflow`、引数を`.arg`で保存)を提供するに留まる([Export PAD Flows](https://marketplace.uipath.com/listings/export-power-automate-desktop-pad-flows))。

一方で、PADデザイナーの「拡張コピー&ペースト機能」(2021 wave 1で導入)はクリップボード経由でテキスト表現を書き出せることが公式リリースノートに明記されており([Enhanced copy and paste feature](https://learn.microsoft.com/en-gb/power-platform-release-plan/2021wave1/power-automate/enhanced-copy-paste-feature))、実例としてGitHubの個人リポジトリ`Hardik-S/geodata`に実データが残っている([raw file](https://raw.githubusercontent.com/Hardik-S/geodata/main/geodata%20PAD%20Flow%20as%20text.txt))。この構文は`SET 変数 TO 式`、`LOOP FOREACH 項目 IN コレクション`〜`END`という明示的な開始・終了を持つブロック構造、`名前空間.モジュール.アクション名 パラメータ名: 値 ... 出力パラメータ=> 変数名`というアクション呼び出し、`$'''...'''`のトリプルクォート文字列リテラル、`**REGION`/`**ENDREGION`によるグルーピングという、驚くほど規則的な行指向DSLである。これは**永続フォーマットそのものではなく、デザイナーのクリップボード用中間表現**と考えるのが妥当だが、構文が「アクションID+名前付きパラメータ辞書+出力変数名」という一貫した形を取っているため、PADの内部データモデルをかなり正確に反映していると推測できる。もう一つの重要な分岐点が**Power Fx対応フロー**の存在だ。v2.39以降、フロー単位でPower Fx(強い型付け、`=`始まりの式、`${式}`文字列補間)を有効化できるが、有効化すると配列インデックスが0始まりから**1始まりに変わり**、変数名が大文字小文字を区別するようになり、`Switch`/`Case`アクションが使えなくなるなど、事実上別の実行モデルになる([Power Fx in desktop flows](https://learn.microsoft.com/en-us/power-automate/desktop-flows/power-fx))。これはパーサー設計上、**単一の固定スキーマで全バージョン・全モードのPADフローを扱うことはできない**ことを意味し、少なくとも「Power Fx無効/有効」の2モードをフロントエンドで明示的に分岐させる必要がある。なお公式開発者向けAPI「Work with desktop flows using code」はDataverse Web API経由でフロー一覧・入出力JSONスキーマの取得・実行・キャンセルを提供するが、**フロー内部のアクション列定義そのものを返すエンドポイントは存在しない**([desktop-flow-public-apis](https://learn.microsoft.com/en-us/power-automate/developer/desktop-flow-public-apis))。入力の調達方法として実務上現実的な選択肢は、(1)クリップボードのコピー結果をユーザーにテキストファイルとして保存してもらう、(2)PADコンソールのUI上でアクションを選択してコピーし、プログラム的にWindowsクリップボードを読む、の2つに絞られる。

## UI操作系アクションはpywinauto/pyautoguiへ機械的に落とし込めるが、ドラッグ&ドロップや画像待機は手作業の補完が要る

PADのUIオートメーションアクションは「物理モード」(マウス/キーボードを実際に乗っ取って操作)と「シミュレートモード」(対象をフォアグラウンド化せずプログラム的に操作)の2方式を持つ([UI automation actions reference](https://learn.microsoft.com/en-us/power-automate/desktop-flows/actions-reference/uiautomation))。これはpywinautoの`click_input()`(物理入力相当)と、UIAパターン経由の`invoke()`/`click()`(メッセージ送信相当)の対比にそのまま写し込める。ウィンドウ操作系(`Get window`, `Focus window`, `Set window state`, `Move window`, `Resize window`, `Close window`, `If window`, `Wait for window`)は、pywinautoの`Application.connect()`→`top_window()`で得た`WindowSpecification`に対する`.maximize()`/`.minimize()`/`.close()`/`.move_window()`/`.wait("exists"/"active")`とほぼ1対1で対応することを確認した。唯一「Set window visibility(Hidden/Visible)」に相当する公式pywinauto APIは見つからず、`win32gui.ShowWindow()`(pywin32)併用が実務解と推測される(未確証)。マウス・キーボード系(`Move mouse`, `Send mouse click`, `Send keys`, `Press/release key`)はpyautoguiの`moveTo()`, `click()`, `typewrite()`/`press()`, `keyDown()`/`keyUp()`/`hotkey()`にほぼそのまま移植できる一方、**画像/OCRベースのマウス移動(Move mouse to image / Move mouse to text)**は`pyautogui.locateCenterOnScreen(confidence=...)`で近似できるが、**Block Input**(`ctypes.windll.user32.BlockInput()`直接呼び出しが必要)、**Set key state**(Caps/Num/Scroll Lockトグル、`keyboard`ライブラリ等の追加実装が必要)、**Wait for shortcut key**(グローバルホットキーフック、pyautogui単体では代替不可)は、pyautogui標準APIの範囲を超えるため個別のネイティブAPIラッパーを自作する必要がある。

| PADアクション分類 | 代表アクション | Python対応 | 備考 |
| --- | --- | --- | --- |
| ウィンドウ操作 | Get/Focus/Move/Resize/Close window | pywinauto `WindowSpecification`メソッド群 | Set window visibilityは要pywin32併用(未確証) |
| マウス・キーボード(座標系) | Move mouse, Send mouse click, Send keys | pyautogui `moveTo/click/typewrite/press` | 「Relative to: Active/Foreground window」はpywinautoの`rectangle()`でオフセット計算が必要 |
| 待機系 | Wait for window(content) | pywinauto `wait()`/`wait_not()` + `timings.wait_until_passes` | Wait for image/mouse/shortcut keyはpywinauto対象外、自前ポーリングループが必要 |
| 画像/OCR系 | Move/Wait for image | pyautogui `locateOnScreen` + 自作ポーリング | pyautoguiに専用の待機APIはない |
| OS低レベル機能 | Block Input, Set key state | `ctypes.windll.user32`直接呼び出し | pywinauto/pyautoguiいずれにも標準APIなし |

変数データ型(Text/Numeric/Boolean/List/Datatable/Datarow/Custom object)はPythonの`str`/`int・float`/`bool`/`list`/`pandas.DataFrame`または`list[dict]`/`dict`への変換が自然であり、2022年以降サブフローがこれらの型を入出力できるようになったことも確認できた([Variable data types](https://learn.microsoft.com/en-us/power-automate/desktop-flows/variable-data-types))。エラーハンドリングは「On block error」(ブロック単位の再試行+Exception handling mode)、「Throw custom error」、「Get last error」の3層構造を持ち、これは`try/except`+カスタム例外クラス+リトライループ(または`tenacity`ライブラリ)という一般的なPythonパターンに自然対応する([Second level of error handling](https://docs.microsoft.com/en-us/power-platform-release-plan/2020wave2/power-automate/second-level-error-handling-power-automate-desktop))。ただし「Get last error」の戻り値の正確なフィールド構成、および`flowcontrol`アクションリファレンスページ自体の一次確認は今回未完了であり、実装前に`actions-reference/flowcontrol`の直接確認が必要である。重要なのは、**この対応表自体がオリジナルの一次整理である**という点だ——Web検索では、PADアクションとpywinauto/pyautoguiのAPIを明示的に1対1で対応付けた既存記事・ライブラリは一件も見つからなかった。

## UIAセレクタは属性単位で翻訳できるが、AutomationIdの不安定性とElectron系UIが変換後も壊れやすさを引き継ぐ

PADのUI要素セレクタは`:desktop > window[Name="Notes.txt - Notepad"][Process="Notepad"]`のような**階層的なブラケット記法の文字列**であり、UIA/MSAA/UIA3 Rawの3キャプチャモードに対応する([Build a custom selector](https://learn.microsoft.com/en-US/power-automate/desktop-flows/build-custom-selectors)、[Automate using UI elements](https://learn.microsoft.com/en-us/power-automate/desktop-flows/ui-elements))。pywinautoは`win32`バックエンドと`uia`バックエンドを持ち、`auto_id`・`control_type`・`framework_id`は明示的に「UIAutomation要素向け」と注記されているため、PADの`AutomationId`/`ControlType`属性を渡すには**必ず`backend="uia"`を選ぶ必要がある**([pywinauto.findwindows docs](https://pywinauto.readthedocs.io/en/latest/code/pywinauto.findwindows.html))。属性レベルの対応は概ね素直で、PADの`Name`はpywinautoの`title`(UIAの`Name`プロパティ相当)に、`AutomationId`は`auto_id`に、`>`で連結された階層は`child_window()`のネストに対応すると考えられる。一方で**非対応・非対称な部分も多い**。PADの`Process`属性はセレクタの階層ノードではなく、pywinauto側では`Application.connect(process=...)`というアプリ接続レベルの別概念として扱われる。PADの演算子(`Contains`/`Starts with`/`Ends with`/正規表現)には専用キーワードがなく、`title_re`/`class_name_re`への**正規表現への機械的な書き換え**(`.*foo.*`, `^foo`, `foo$`)が必要になる。PADの「複数セレクタの順序フォールバック」機構はpywinautoに標準搭載されておらず、呼び出し側で例外処理によるリトライロジックを自作する必要がある。逆方向では、pywinautoが要求する`backend`選択、`top_level_only`/`visible_only`/`enabled_only`といった検索スコープフラグ、`handle`(Win32ウィンドウハンドル)はPADのセレクタ情報には存在せず、変換時に**補完・推測で埋める必要がある情報**である。

| PAD属性/演算子 | pywinauto対応 | 制約 |
| --- | --- | --- |
| `Name` | `title` | UIAの`Name`プロパティ相当 |
| `AutomationId`(推測含む) | `auto_id` | `backend="uia"`が必須 |
| `Process` | `Application.connect(process=...)` | セレクタ条件ではなく接続レベルの概念 |
| `Contains`/`Starts with`/`Ends with` | `title_re`/`class_name_re` | 正規表現への変換が必要、専用キーワードなし |
| 複数セレクタのフォールバック | 標準API無し | 呼び出し側で例外ハンドリングを自作 |

より本質的な問題は、**セレクタを変換できても長期的な脆さまでは解決できない**ことだ。Microsoft自身のドキュメントは`AutomationId`について「アプリのリリース/ビルドが変わると安定性の保証はない」と明記しており([AutomationElement.AutomationIdProperty](https://msdn.microsoft.com/en-us/library/ms598108))、これはPAD側・pywinauto側に共通するリスクである。仮想化リスト(スクロール外の行がUIAツリーに実体化されない)は両ツールで同様に失敗し、Microsoft公式には`ItemContainer`/`VirtualizedItem`パターンでの対処が明記されている([Retrieve a Virtualized Item](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-howto-retrieve-virtualized-item))。Electron/CEFアプリに対してはPAD自身が標準UIAの限界を認め「UIA3 Rawモード」への切替を公式に推奨しているが、**pywinautoには同等の「生ツリーモード」切替機能が標準ドキュメント上確認できず**、Chrome 138以降のネイティブUIA化のような外部要因の改善に依存する部分が大きい([Chrome Developers Blog](https://developer.chrome.com/blog/windows-uia-support-update))。つまり、PAD側でUIA3 Rawを使わざるを得なかった要素は、pywinautoへ変換してもUIAバックエンドでは同様に取得困難であり、ブラウザ自動化系ライブラリ(Playwright等)や座標/画像ベースのフォールバックを変換ツール側で別途用意する必要がある。マルチモニタ・DPIスケーリング環境での座標ズレもpywinautoの既知の不具合として報告されており、座標ベースのアクション変換では注意が必要である。

## PAD→Python変換の先行事例はゼロに近く、業界はRPA間移行を「書き直し推奨」で合意している

今回の調査でPADフローをPython(または他言語)へ直接変換する専用のOSSプロジェクトは一件も見つからなかった。見つかったのはむしろ逆方向——`pypowerautomate`はPythonから**クラウドフロー**のJSONを生成するツールであり([PyPI](https://pypi.org/project/pypowerautomate/))、Microsoft自身の最新戦略も「PADからPythonスクリプトを呼び出す」方向(2026年に任意のローカルPythonバージョンを実行可能にする機能)に向かっている。これはMicrosoftが「PADフローをPythonへ変換する」のではなく「PADフロー内でPythonを混在実行させる」アプローチを選んでいることを示唆する一次証拠である。他のRPAベンダー間でも状況は類似している。Robocorpの**Converter Accelerator**はUiPath/Blue Prism/Automation Anywhereのプロジェクトをオープンソースの Robot Frameworkへ変換する機能を持つが、UiPathのState Machine型ワークフローは非対応と明記され、ページ自体も2022年12月更新のまま保守状況が不明である([Robocorp docs](https://robocorp.com/docs-robot-framework/conversion/tools))。Blueprint SystemsのMigrateやKanerika FLIPのような商用アクセラレータは「エンドツーエンド変換」を主張するが、同時に「複雑なカスタムアクティビティは再構築が必要になる場合がある」と自ら限界を認めている([Blueprint docs](https://blueprint.helpdocs.io/l/en/article/ajmht7bg69-migrate-import-export))。Automation Anywhereのコミュニティスタッフは「異なるRPAツール間でのボットコード移行は、各製品が独自のアーキテクチャ・フレームワーク・コードバインディングを持つため実現不可能」と明言しており([Automation Anywhere forum](https://community.automationanywhere.com/developers-forum-36/can-i-migrate-blue-prism-or-uipath-code-to-automation-anywhere-7439))、UiPathフォーラムの実務者も繰り返し「手作業での再構築しかない」と証言している。学術研究側も「RPAスクリプト自体のコード変換」を直接対象とした査読付き論文は見当たらず、最も近いのは2026年のarXiv論文「AutoRPA」だが、これはLLMエージェントの操作ログから新規にRPA関数を**合成**する逆方向の研究であり、既存フローの**トランスパイル**とは問題設定が異なる([arXiv:2605.21082](https://arxiv.org/abs/2605.21082))。

これらの事実が示す構造的な教訓は明確だ。Blueprintのブログは移行の技術的複雑さの核心を「条件分岐・ループ・待機条件などのロジック要素はツール間で構造が大きく異なる」「例外処理へのアプローチが異なる」「要素識別(セレクタ)の扱い方が異なる」の3点に整理している([Blueprint blog](https://www.blueprintsys.com/blog/rpa/what-are-technical-complexities-migrating-between-rpa-platforms))。この3点は前節・前々節で確認したPAD特有の課題(Power Fx有効/無効での型モデル分岐、On block errorの3層構造、UIAセレクタの脆さ)と完全に一致する。つまり**PAD→Python変換が難しいのはPAD固有の問題ではなく、GUIベースRPA変換一般に内在する構造的な難所**であり、本プロジェクトは「前例のない挑戦」であると同時に「前例が示す落とし穴を事前に回避できる」立場にもある。実務上の結論としては、**完全自動変換を目標に据えず、人手レビューを前提とした半自動変換支援ツール**として設計することが、業界の一致した経験則と整合する。

## パーサー→IR→コードジェネレータの三層構成とVisitorパターンが設計の土台になる

一般的なトランスパイラ/コードジェネレータの黄金律は「字句解析→構文解析(AST)→中間表現(IR)→コード生成」のパイプラインを独立したパスに分離することであり、Jinjaのようなテンプレートエンジンのコンパイラ自体も「Lexer→Parser→識別子解析→コードジェネレータ」の4段構成を踏襲している([Dismantling Jinja](https://pycon-archive.python.org/2012/schedule/presentation/246))。IR設計の統一原則は「各処理パスがローカルな情報だけで判断できるようにすること」であり([What I talk about when I talk about IRs](https://bernsteinbear.com/blog/irs/))、PADのような「アクションのシーケンス+If/Loopの制御フロー+変数スコープ」を表現するには、CFGやSSAのような低レベル最適化志向のIRは過剰で、むしろ**構造化された制御フロー(If/Loop/Sequenceノードを木構造で保持する高レベルIR)+シンボルテーブルによる変数スコープ管理**が適している。この設計はBlocklyの実例と直接共鳴する。Blockly公式ドキュメントは「言語コードジェネレータ(インデント・コメント整形などの言語レベル規則)」と「ブロックコードジェネレータ(各ブロック型×各言語で1関数)」の2層分離を明確に定義しており([Blockly: Generating Code](https://docs.blockly.com/guides/create-custom-blocks/generating-code))、これはPADアクション種別ごとの変換ロジックとPython言語レベルの整形規則(インデント管理、import集約)を分離する設計にそのまま応用できる。対照的にNode-REDは、JSONフロー定義から**コードを生成せず**ノードオブジェクトを直接インスタンス化して実行するインタプリタ型アーキテクチャを取っている([Node-RED deploy discussion](https://groups.google.com/g/node-red/c/cl3mFPVYhDg))。これは代替アーキテクチャとして検討に値するが、本プロジェクトの目的が「人間が読める・保守できるPythonソースを出力すること」である以上、**Blockly型のコード生成アプローチの方が目的に合致する**。

コード生成の実装手段としては、Python標準`ast`モジュール+`ast.unparse`+`black`による整形と、LibCSTのような可逆CSTの2択がある。LibCSTはコメント・空白を完全保持できる強みを持つが、これは**既存コードの編集(codemod)**に向いた特性であり、既存Pythonコードを編集するのではなく新規生成する本プロジェクトでは必要性が薄いと判断できる。むしろアクション単位の変換パターンが規則的であることを踏まえると、**Jinja2的なテンプレートベースのコード生成**(各アクション種別に対応するテンプレート)と、インデント・変数スコープ管理が必要な部分だけASTレベルで組み立てるハイブリッド構成が、実装コストに対して合理的である。「忠実な1:1変換」と「意味を保った最適化」のトレードオフについては、業界の議論は一貫して**段階分離**を支持している——Hacker Newsの議論でも「パリティ(振る舞いの同一性)を第一段階とし、イディオム的なリファクタリングは別フェーズで行うべき」という意見が共有され([HN discussion](https://hn.nuxt.dev/item/47120899))、COBOL→Javaの逐語的トランスコーダに対する批判も「出力は合法だが慣用的ではなく、移行の目的である保守性向上を損なう」と指摘している([COBOL migration critique](https://www.semanticdesigns.com/Products/Services/EraneaNACA.html))。未対応アクションへの対処としては、XSLTCの正式な「フォールバック」機構(未対応要素はフォールバック子要素があれば使用し、無ければ実行時エラー)や、Rosettaプロジェクトの「変換不能な構文は元のソースをコメントとして出力し`TODO`マーカーを付ける」という方針が参考になる([Xalan XSLTC Fallback](https://xalan.apache.org/xalan-j/apidocs/src-html/org/apache/xalan/xsltc/compiler/Fallback.html)、[Rosetta#24](https://www.github.com/andry-tino/Rosetta/issues/24))。複数のプロジェクトで「サイレントに握りつぶす」ことは明確に否定されており、テスト戦略としては、代表的なPADフロー定義からPythonコードを生成し、ゴールデンファイルとしてGit管理した上で、テキスト比較に加えて**生成コードを実際に`py_compile`/`ast.parse`に通して構文的正しさまで検証する**二層構成が実務的である([openapi-nexus golden testing](https://docs.rs/crate/openapi-nexus/latest/source/docs/src/golden_testing.md))。

## 推奨アーキテクチャ:フェーズ分けとリスク対応策

以上の調査結果を統合すると、推奨アーキテクチャは**「テキストDSLフロントエンド→高レベルIR→Visitorベースのハイブリッドコードジェネレータ(テンプレート+AST)」**の三層構成となる。フロントエンドはPower Fx無効/有効の2文法に対応する独立したパーサーを持ち(共通のIRへ正規化)、各アクション呼び出し行を「アクションID+パラメータ辞書+出力変数名」のノードとして読み込む。IRはCFG/SSAのような低レベル最適化志向ではなく、`Sequence`/`If`/`Loop`/`ActionCall`ノードを木構造で保持する高レベルIRとし、変数スコープはIRノードの属性ではなくシンボルテーブル(名前→型・スコープ・定義位置)で別管理する。コードジェネレータはBlockly型の「言語レベルジェネレータ(インデント・import集約)×アクション種別ジェネレータ(1アクション=1関数)」の2層分離とし、各アクション種別ジェネレータはテンプレート(Jinja2的な文字列断片)を返し、それらをASTレベルで組み立てて最終的に`black`で整形する。未対応アクションは既定で変換を完走させつつ`# TODO: unsupported action <ActionType>`コメント+元のPAD定義をそのまま埋め込むフォールバックとし、CI用途には全未対応アクションで停止する「厳格モード」も用意する。

フェーズ分けは以下の4段階を推奨する。**フェーズ0(フォーマット確定)**では、実機PADでクリップボードコピーのテキストDSLとUI要素セレクタのテキストエディタ表現を多数のアクション種別・両Power Fxモードで収集し、`geodata`リポジトリの構文を拡張した文法(EBNF)を確定する。ここで「ソリューションエクスポートのSchema V2バイナリ」への対応は明確にスコープ外とし、クリップボードDSL経路のみを公式入力経路として扱う判断を早期に確定することが重要である。**フェーズ1(コア変換器)**では、ウィンドウ操作・変数設定・If/Loop制御フロー・エラーハンドリングという「構造的に確実な」アクション群のみを対象にパーサー→IR→コードジェネレータの三層を実装し、ゴールデンファイルテストを整備する。**フェーズ2(UI操作・セレクタ変換)**では、マウス/キーボード・UIオートメーションアクションとセレクタパーサーを追加し、`backend="uia"`固定での`child_window()`生成、演算子の正規表現変換、複数セレクタのフォールバックリトライラッパーを実装する。**フェーズ3(ロングテール対応と診断機能)**では、画像/OCR系・Block Input等のネイティブAPI依存アクションの個別ラッパーを追加し、未対応アクションの構造化診断レポート(何件変換できたか/できなかったか)を出力する機能を仕上げる。

主要なリスクと対応策を整理すると、第一に**入力フォーマットの経年変化**(Schema V1→V2のバイナリ化のような非告知の変更)に対しては、パーサーをバージョン検出可能な形で分離し、未知の構文に遭遇した場合は即座に失敗させて黒塗りの誤変換を防ぐ設計が対応策となる。第二に**セレクタの実行時脆さの引き継ぎ**(AutomationId不安定性、仮想化リスト、Electron系UI)に対しては、変換ツールの責務を「PADが記録したセレクタの忠実な翻訳」に限定し、「より安定したセレクタの推奨」のような付加的なリファクタリング提案は別のオプトイン機能として分離する。第三に**未検証領域の多さ**(Get last errorの戻り値構造、Set window visibilityのpywinauto対応、flowcontrolアクションリファレンスの詳細)に対しては、実装着手前に該当する公式ドキュメントページの直接確認と、実機PADでの動作検証を必須のフェーズ0タスクとして組み込む。第四に**完全自動変換への過度な期待**に対しては、業界の一致した経験則(RPAツール間移行は書き直しが現実的)を踏まえ、プロジェクトのゴールを「開発者の手戻りを減らす半自動変換支援+診断レポート」と明確に設定し、生成コードには常にレビューを前提とした警告・トレーサビリティコメント(どのPADアクションから生成されたか)を残すことで、過大な成果期待によるプロジェクト失敗を防ぐ。
